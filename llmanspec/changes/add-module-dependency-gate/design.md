# 设计决策:模块依赖方向门禁

## D1 冻结而非收紧

声明表 = 当前实测边集。理由:先止住"新环不再长"(增量违规归零),断环由后续 change 以机械搬移完成、每删一条边就同步收窄声明表。若现在就收紧(声明目标 DAG),门禁落地即红,迫使同 change 内夹带结构重构——违背最小改动与可验证性。

## D2 边的口径:文件级解析 → 顶层模块

- 节点 = `packages/core/src` 下第一层目录名 + 根文件;`src/index.ts` 为公共 barrel,**豁免**(它按定义 import 一切)。
- 边 = 文件相对导入(`../`、`../../`)经路径解析落到**异于来源模块**的顶层模块;`import type` 与值导入同权(类型耦合也是耦合)。
- 包内 `./` 导入、同模块跨文件导入不计;`node:`/裸包名导入不计(纯域纪律另由 r3/oxlint 守护)。

## D3 规则归属 monorepo-structure r72

- 与 r1(布局对账)/r3(纯域)/r67(模板对账)同域:工程结构守卫。
- 声明表的 SSOT = 门禁测试内的 ALLOWED 表(规则文本不复制边集,避免双权威;规则只钉机制)。
- @executable:执行命令 `bun test tests/unit/module-dependency-parity.test.ts` 退出 0(与 r67 同 seam)。

## D4 违例报告形态

逐条 `[文件] 模块A → 模块B(不在允许表)`;同时报告"声明表中已无对应实现的边"(表漂移检测),防止断环后忘收窄。

## 备选与取舍

- **dependency-cruiser 等外部工具**:否——引入新依赖 + 配置面,不如 60 行自研扫描与 r67/r70 同型可审。
- **ESLint no-restricted-imports per 目录**:表达不了"边集"语义(它是单文件视角)。
- **顺手断环**:否——D1 已述,分开走。
